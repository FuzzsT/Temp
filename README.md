# Cube7 LaserOS Full Bridge 0.4.0 — Renderer Tap / Format3 / Official Transport DRY-RUN

Windows x64 bridge for analyzing **LaserOS 0.18.1** and translating its rendered vector frames into the confirmed data format used by the target **Laserworld CUBE 7**.

## What changed in 0.4.0

0.3.x attempted to make LaserOS recognize a virtual network LaserCube. 0.4.0 takes a different path: it taps the renderer before LaserOS hardware authentication/device-ready logic.

```text
LaserOS 0.18.1
    ↓ ldRendererOpenlase begin/vertex/end
LaserOSHook.dll
    ↓ RendererFrame
CubeFormat3Translator
    ↓ 16-bit XY + state/angle + palette index
Cube dataFormatType=3
    ↓
CubeOfficialProtocol
    ↓ plaintext 0xAD / 0xA5 frames
DRY-RUN capture files
```

This means Projector Setup may still display **NO LASER** while the renderer tap can independently capture geometry generated by LaserOS.

Official application analysis confirms the transport markers:

```text
0xAB → 0x8B   session handshake
0xAD          first data fragment
0xA5          continuation fragment
0x85          data ACK
```

The community-style guessed `FFE2 + AA/CMD/LEN/checksum` protocol is not used as the basis of this release.

## Cube dataFormatType=3

The Cube application data recovered from `Cube.zip` shows that type 3 uses a 2-byte big-endian point count followed by 6 bytes per point:

```text
X      16-bit big-endian
Y      16-bit big-endian
state  8-bit: first/end flags + angle bits
color  8-bit palette index
```

The recovered application palette contains **250 entries**. The translator maps LaserOS renderer RGB to the nearest entry in that palette and maps renderer XY from `[-1,+1]` to `[0,65535]`.

## Capture artifacts

Every decoded renderer frame is written at three levels:

```text
captures/<timestamp>/renderer-frames.ndjson
captures/<timestamp>/renderer-frames.bin

captures/<timestamp>/cube-format3.ndjson
captures/<timestamp>/cube-format3.bin

captures/<timestamp>/cube-transport-plaintext.ndjson
captures/<timestamp>/cube-transport-plaintext.bin
```

`cube-format3.bin` stores each translated layer payload as:

```text
uint32 little-endian payload length
payload bytes
```

`cube-transport-plaintext.bin` stores each official transport frame as:

```text
uint32 little-endian frame length
0xAD/0xA5 frame bytes
```

The transport serializer uses the verified runtime values `bufferMax=244` and `dataFormatType=3`. The first data chunk capacity is `244-47`; continuation chunk capacity is `244-5`.

## Official crypto regression

0.4.0 also contains a pure/offline reproduction of the v26 application AES-128-CTR wrapper. It is regression-tested against the known `0xAB` connection vector.

Rules reproduced by the test:

- command byte remains plaintext;
- at most the next 240 body bytes are AES-CTR transformed;
- short bodies use CryptoJS-compatible zero padding to a 16-byte boundary;
- body bytes after the first 240 remain plaintext.

This crypto implementation is **not connected to live BLE in 0.4.0**. Post-handshake pattern traffic requires the session-specific key/IV derived from the actual `0x8B` response; using the default connection crypto for live pattern frames would be incorrect.

## Safety state

0.4.0 is deliberately fail-closed:

- no live vendor BLE payload writes;
- no automatic `ENABLE_LASER_OUTPUT`;
- no automatic ARM;
- no interlock/E-stop bypass;
- renderer and transport outputs are files only;
- `physicalOutput=false` and `dryRun=true` are recorded in capture metadata.

The virtual LaserCube responder remains available for protocol diagnostics but is disabled in the default 0.4 configuration.

## Start

Close LaserOS first, then run:

```bat
start-full.cmd
```

Early injection starts LaserOS with `LaserOSHook.dll` loaded before application initialization. A healthy renderer-tap run should contain:

```text
[hook] connected
[renderer] frame summary: ...renderer-frames.ndjson
[format3] dry-run summary: ...cube-format3.ndjson
[transport] plaintext dry-run summary: ...cube-transport-plaintext.ndjson
[renderer] frame=1 points=... format3+AD/A5=dry-run
```

If LaserOS still shows `NO LASER`, that alone is not a failure of 0.4.0. The decisive evidence is whether `renderer-frames.ndjson` receives frames while content/preview is running.
